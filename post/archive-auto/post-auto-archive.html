Don't Maintain Your Archive. Automate It.

February 28, 2026 • 12 min read

Any task you do more than twice by hand is a task you've already decided to do wrong. Here's how to make your blog archive update itself.

The most dangerous kind of work is the kind that feels productive but isn't. Manually updating an archive page is a perfect example. You publish a post, you open archive.html, you copy a few lines of HTML, change the date, save the file, push again. Takes maybe two minutes. Totally fine — until the one time you're in a hurry and skip it, and your archive silently lies to your readers for the next six months.

The right response to that failure mode isn't to be more disciplined. It's to make the failure impossible. That's what this post is about. We're going to make archive.html a derived artifact — something generated automatically from the posts you've already written — so it literally cannot fall out of sync. The whole thing runs on a free GitHub feature, takes about an hour to set up, and then you never think about it again.

Who is this for?

You need to know basic HTML and have used Git at least once. That's it. I'll explain every GitHub Actions concept from scratch, and the Python script is short enough that you don't need Python experience — just the ability to read code and follow what it's doing.

The Laziness Principle

Good programmers are lazy in a specific way. They hate doing the same thing twice. Not because they're unmotivated — usually the opposite — but because repetition is a signal. If you're doing something manually over and over, you've spotted a pattern, and patterns are exactly what computers are for.

Look at what a post card in index.html already contains: the title, the link, the date, the excerpt. Everything the archive page needs. It's all right there. The archive isn't missing information — it's just a different view of information that already exists. So why are we duplicating it by hand?

The answer, of course, is that we shouldn't be. index.html should be the single source of truth. The archive is a derived output — generated from the posts, not maintained alongside them. Once you see it that way, the solution is obvious: write a script that reads one file and generates the other, and run it automatically on every push.

How It Actually Works

Before writing a single line of code, get the shape of the solution clear in your head. There are three actors: you, GitHub Actions, and GitHub Pages. They each do exactly one thing.

You write posts. GitHub Actions runs a Python script that regenerates the archive. GitHub Pages serves the result. That's it. What's nice about this division is that none of them need to know much about the others.

The thing worth pausing on is Step 2. The script rewrites archive.html on the runner's temporary filesystem — the throwaway virtual machine GitHub spins up to run your workflow. That modified file gets packaged and shipped to GitHub Pages in Steps 3 and 4. Your actual repository is never committed to. No bot commits, no extra git history, no clever hacks to prevent infinite loops. The runner does its work and disappears.

The right mental model

The runner is a disposable photocopier. It makes a copy of your repo, edits that copy, and faxes the result to GitHub Pages. The original in your repo is untouched. Then the photocopier is shredded. This is the key insight — you're not fighting git, you're just using the filesystem.

Three Files. That's the Whole System.

I like solutions that fit in your head. This one has three pieces. Once you understand what each one does, you'll never need to look up how any of it works — you'll just know.

Table 1. The three files and what each one is responsible for.
File Location in repo Role Do you edit it?
deploy.yml .github/workflows/ Tells GitHub Actions what to do and when Rarely — only to add new steps
generate_archive.py scripts/ Parses index.html and regenerates archive.html No — it is self-contained
archive.html repo root The output — overwritten on every deploy Never — it is auto-generated

File 1: The Workflow — deploy.yml

A GitHub Actions workflow is a YAML file that tells GitHub what to run, on which machine, and in what order. YAML is just a configuration format — indentation matters (think Python), and colons separate keys from values. Don't be intimidated by it. Read it like a recipe.

Here's the complete workflow. I've commented every non-obvious line, because the worst thing about YAML configs is that they look like boilerplate until suddenly one missing line breaks everything.

yaml 
# The name shown in the GitHub Actions tab
name: Build & Deploy to GitHub Pages

on:
  push:
    branches:
      - main        # Run this workflow whenever you push to main
  workflow_dispatch: # Also lets you click "Run workflow" manually
                     # in the GitHub → Actions tab

# Three permissions required by GitHub Pages deployments.
# Remove any of these and the deploy step will fail.
permissions:
  contents: read    # Read repo files
  pages: write      # Publish to GitHub Pages
  id-token: write   # Authenticate the deployment securely (OIDC)

# If you push twice quickly, cancel the older run.
# Prevents two deploys racing each other.
concurrency:
  group: pages
  cancel-in-progress: true

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest  # Spins up a fresh Ubuntu virtual machine

    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}  # Shows live URL in summary

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4
        # Downloads your entire repo into the runner's filesystem.
        # After this step, all your files exist at /home/runner/work/

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"
        # Installs Python. The script uses only stdlib, so no pip install needed.

      - name: Generate archive.html
        run: python scripts/generate_archive.py
        # Runs the parser. Rewrites archive.html on the runner.
        # Your repo on GitHub is NOT changed.

      - name: Setup GitHub Pages
        uses: actions/configure-pages@v4
        # Required boilerplate — prepares the Pages deployment context.

      - name: Upload site files
        uses: actions/upload-pages-artifact@v3
        with:
          path: '.'
        # Zips up everything from the repo root (including the freshly
        # generated archive.html) and registers it as a Pages artifact.

      - name: Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4
        # Publishes the artifact. Your site is live.
One thing you have to do manually

Go to your repo on GitHub → Settings → Pages → Source and select GitHub Actions. You only do this once. Skip it and the deploy step fails with a cryptic permissions error that will send you down a frustrating rabbit hole.

File 2: The Engine — generate_archive.py

This is the interesting part. The script has one job: read index.html, pull the data out of every post card, sort by date, group by year and month, and write a complete archive.html. It uses only Python's standard library — nothing to install, nothing to configure.

What HTMLParser actually does

Python's built-in HTMLParser reads HTML top-to-bottom and fires callback methods as it goes: handle_starttag when it hits an opening tag, handle_endtag on a closing tag, and handle_data when it encounters plain text. We use simple boolean flags to remember where we are in the document. It sounds fancier than it is — it's really just a state machine.

python 
from html.parser import HTMLParser
import re

class PostCardParser(HTMLParser):
    def __init__(self):
        super().__init__()
        self.posts = []          # Final list of parsed posts
        self._in_article  = False
        self._in_title_a  = False
        self._in_excerpt  = False
        self._in_meta     = False
        self._current     = {}   # Buffer for the post being parsed
        self._meta_text   = ""

    def handle_starttag(self, tag, attrs):
        attrs = dict(attrs)

        # Detect the opening of a new post card:
        #   

        if tag == "article" and "post-card" in attrs.get("class", ""):
            self._in_article = True
            self._current = {
                "title": "", "href": "", "excerpt": "",
                "date_str": "", "read_time": ""
            }

        if not self._in_article:
            return  # Ignore everything outside a post card

        # Detect the title heading:
        #   

        if tag in ("h2","h3","h4") and "post-card-title" in attrs.get("class",""):
            self._current["_title_open"] = True

        # Detect the link inside the title heading:
        #   
        if tag == "a" and self._current.get("_title_open") and not self._current["href"]:
            self._in_title_a = True
            self._current["href"] = attrs.get("href", "")  # Grab the URL

        # Detect the excerpt paragraph:
        #   

        if tag == "p" and "post-card-text" in attrs.get("class",""):
            self._in_excerpt = True

        # Detect the metadata div (holds date + read time):
        #   

        if tag == "div" and "post-meta" in attrs.get("class",""):
            self._in_meta   = True
            self._meta_text = ""

    def handle_data(self, data):
        # Accumulate text while inside relevant elements.
        # This fires for every piece of plain text, including
        # whitespace — the .strip() calls later clean that up.
        if self._in_title_a: self._current["title"]  += data
        if self._in_excerpt: self._current["excerpt"] += data
        if self._in_meta:    self._meta_text           += data

    def handle_endtag(self, tag):
        if tag == "a"   and self._in_title_a: self._in_title_a = False
        if tag == "p"   and self._in_excerpt: self._in_excerpt  = False

        # When the meta div closes, parse the accumulated text
        # to extract date ("November 28, 2025") and time ("8 min read")
        if tag == "div" and self._in_meta:
            self._in_meta = False
            m_date = re.search(r'([A-Z][a-z]+ \d{1,2}, \d{4})', self._meta_text)
            m_time = re.search(r'(\d+ min read)',                 self._meta_text)
            if m_date: self._current["date_str"]  = m_date.group(1)
            if m_time: self._current["read_time"] = m_time.group(1)

        # When the article closes, save the completed post dict
        if tag == "article" and self._in_article:
            self._in_article = False
            self._current.pop("_title_open", None)
            if self._current.get("title") or self._current.get("href"):
                self.posts.append(dict(self._current))

Sorting and grouping

Once the parser has a list of raw post dicts, two things need to happen: sort them (newest first) and group them (by year, then month). The sorting is why we convert the date string into an actual datetime object — you can't sort "November 28, 2025" and "March 10, 2026" alphabetically and get the right answer. But you can sort two datetime objects and always get the right answer.

python 
from pathlib import Path
from datetime import datetime
from collections import defaultdict

ROOT         = Path(__file__).parent.parent  # Repo root
INDEX_FILE   = ROOT / "index.html"
ARCHIVE_FILE = ROOT / "archive.html"

def parse_posts(index_path):
    html   = index_path.read_text(encoding="utf-8")
    parser = PostCardParser()
    parser.feed(html)

    posts = []
    for p in parser.posts:
        date_obj = None
        if p["date_str"]:
            try:
                # "November 28, 2025"  →  datetime(2025, 11, 28)
                date_obj = datetime.strptime(p["date_str"].strip(), "%B %d, %Y")
            except ValueError:
                pass  # Malformed date — post still included, sorts last

        posts.append({**p, "date_obj": date_obj})

    # Sort newest → oldest
    posts.sort(key=lambda p: p["date_obj"] or datetime.min, reverse=True)
    return posts


def group_posts(posts):
    # Produces:  { 2026: { 2: [post, …], 1: [post] }, 2025: { 12: [post] } }
    grouped = defaultdict(lambda: defaultdict(list))
    for p in posts:
        year  = p["date_obj"].year  if p["date_obj"] else "Unknown"
        month = p["date_obj"].month if p["date_obj"] else 0
        grouped[year][month].append(p)
    return grouped
Why defaultdict?

A regular Python dict throws a KeyError if you access a key that doesn't exist yet. A defaultdict just creates it with a sensible default on first access. It's a small thing, but it lets you write grouped[year][month].append(p) without three lines of "does this key exist yet?" boilerplate above it. Less noise, same meaning.

Following One Post All the Way Through

Abstract explanations only get you so far. Let's trace one concrete post through the whole system so you can see exactly what happens at each step. Say you add this to index.html:

html 
<article class="post-card">
    <img src="https://images.unsplash.com/photo-xxx?w=800" alt="AI">
    <div class="post-card-body">
        <h2 class="post-card-title">
            <a href="./post/intro-to-transformers/post.html">
                An Introduction to Transformer Networks
            </a>
        </h2>
        <p class="post-card-text">
            How the attention mechanism replaced recurrence in modern NLP.
        </p>
        <div class="post-meta">
            <i class="far fa-calendar"></i> March 10, 2026
            <span class="ms-3"><i class="far fa-clock"></i> 9 min read</span>
        </div>
    </div>
</article>

The parser chews through that HTML and spits out this dict:

python 
# What the parser produces for the article above:
{
    "title":     "An Introduction to Transformer Networks",
    "href":      "./post/intro-to-transformers/post.html",
    "excerpt":   "How the attention mechanism replaced recurrence in modern NLP.",
    "date_str":  "March 10, 2026",
    "date_obj":  datetime(2026, 3, 10),   # Added by parse_posts()
    "read_time": "9 min read"
}

Because datetime(2026, 3, 10) is newer than everything else, it sorts to position zero. It lands in grouped[2026][3] — year 2026, month 3. The render function picks that up, wraps it in the right HTML, and drops it under a "March" heading inside the 2026 year section. Start to finish: under two seconds.

When It Breaks

It will break at some point. Usually it's something trivially fixable, but the error messages from GitHub Actions aren't always helpful. Here are the five failure modes I've hit, and what each one actually means.

Table 2. Common issues and their solutions.
Symptom Likely cause Fix
Post appears with "Date unknown" in the archive Date format doesn't match Month DD, YYYY Use full month name: March 10, 2026 not 03/10/26
Workflow fails: "index.html not found" Script called from wrong directory Ensure deploy.yml runs python scripts/generate_archive.py
Deploy fails with 403 permission error Pages source not set to GitHub Actions Settings → Pages → Source → GitHub Actions
Archive not updated after push Workflow didn't trigger (wrong branch) Confirm you pushed to main, not another branch
Post missing from archive Article element missing class="post-card" Ensure every article has exactly class="post-card"

Where to Take It Next

The system works as-is, but the nice thing about having all your post data flowing through one Python script is that it's trivial to generate other things from it. Two ideas worth pursuing:

Category filtering

Add a <span class="post-category">Mathematics</span> to each post card. The parser extension is maybe ten lines — same pattern as the excerpt extraction. Now you can render a colored badge per post in the archive, and a filter dropdown that narrows by topic. Readers will actually use this.

An RSS feed

By the time the script finishes grouping posts, it has everything needed to write feed.xml too. Roughly thirty extra lines of Python, zero changes to the workflow. RSS feels retro but it has real users — a lot of serious readers still prefer it over algorithmic feeds.

The Real Point

The finished system is three files and maybe a hundred lines of code total. You write a post, push it, and the archive updates. You stop thinking about the archive entirely. That's the goal.

But I think there's a broader lesson here worth naming. The instinct for most people when they encounter a small recurring task is to just do it. It's only two minutes. That's a reasonable instinct for things that genuinely can't be automated. For things that can be, it's a trap. The two minutes adds up, but worse, the cognitive overhead of remembering to do it adds up more. Every manual step is a thing you have to think about. Automation isn't just about saving time — it's about reducing the surface area of things that can go wrong.

The pipeline here is small enough to understand completely. And that matters. Automation you understand is robust. Automation you've cargo-culted from Stack Overflow is a liability. When something breaks at 11pm before a deadline, you want to be able to read the workflow, spot the problem in thirty seconds, and fix it. Build things you can hold in your head.
