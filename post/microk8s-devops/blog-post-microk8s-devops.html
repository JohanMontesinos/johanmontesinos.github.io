Building a Home DevOps Lab on Commodity Hardware

February 23, 2026 • 18 min read

A complete GitOps pipeline — MicroK8s, Flask, PostgreSQL, Helm, ArgoCD, Gitea, and GitHub Actions — running on two repurposed servers and a laptop, with every lesson learned from double NAT, locked ISP modems, and misconfigured git remotes.

There is a particular kind of satisfaction in running production-grade infrastructure on hardware you own. Cloud providers are extraordinary tools, but they abstract away the very friction that teaches you how distributed systems actually work. When a pod fails to schedule because you have genuinely run out of RAM — not because a quota was misconfigured — you learn something that no documentation can convey as efficiently. This post documents the end-to-end construction of a home DevOps lab: a two-node MicroK8s Kubernetes cluster running a containerised Flask application backed by PostgreSQL, deployed via Helm, orchestrated by ArgoCD watching a self-hosted Gitea repository, and continuously delivered by a GitHub Actions self-hosted runner — all on two low-spec servers and a laptop.

View on GitHub.

The project began as a learning exercise and evolved into something closer to a reference architecture. Every component was chosen deliberately: MicroK8s for its low overhead on constrained hardware, Gitea for an on-premise Git server that keeps the GitOps source of truth inside the LAN, and a self-hosted GitHub Actions runner that eliminates the need to expose any port to the internet. The result is a system where a single git push from a laptop triggers a Docker build, a registry push, and a Helm upgrade — all running locally on the control plane node — while ArgoCD independently watches the Gitea repository and self-heals the cluster on any configuration drift.

The Hardware and the Constraints

The lab consists of three devices. A developer laptop serves as the workstation — the only machine that ever needs a graphical interface. Two low-specification servers, each with 4 GB of RAM and a dual-core processor, form the Kubernetes cluster: NODE1 acts as the control plane and hosts all supporting services, while NODE2 serves as a worker node that runs additional application replicas.

Four gigabytes of RAM sounds generous until you account for the Ubuntu OS kernel (~400 MB), the MicroK8s API server and etcd (~250 MB on the control plane), CoreDNS, the Nginx ingress controller, the container registry, PostgreSQL, two Flask/Gunicorn pods, metrics-server, and the GitHub Actions runner. Memory Caution

The kube-prometheus-stack (Prometheus + Grafana + AlertManager) consumes 500–700 MB of additional RAM. On these nodes it will push the control plane into memory pressure and cause OOMKill events. Use metrics-server instead, which provides kubectl top for approximately 30 MB.

The Stack, and Why Each Piece

Every component in the stack was chosen to answer a specific constraint. The application itself is a Flask webapp served by Gunicorn, backed by PostgreSQL, containerised with Docker, and deployed via a Helm chart. The chart controls replica count, resource limits, ingress rules, and the PostgreSQL node selector — ensuring the database always lands on NODE1 where its persistent volume lives.

MicroK8s over K3s or kubeadm

MicroK8s was chosen for its addon system: enabling the local container registry, ingress controller, DNS, and Helm3 each takes a single command. Its containerd runtime is also straightforward to configure for an insecure local registry via hosts.toml, which matters because the registry runs over plain HTTP to avoid certificate management on the LAN.

Gitea for on-premise GitOps

ArgoCD needs a Git repository to watch. Using GitHub directly would mean ArgoCD requires internet access for every sync operation — and any connectivity interruption would break GitOps. Running Gitea as a Docker container on NODE1 keeps the entire source-of-truth loop within the LAN. ArgoCD polls Gitea every three minutes; even a complete internet outage does not affect cluster self-healing.

Self-hosted GitHub Actions runner

The original pipeline design used GitHub's cloud runners to SSH into NODE1 over the internet. This required opening a port on the home router — which proved impossible due to a locked ISP modem in a double NAT configuration. The self-hosted runner inverts the connection direction: NODE1 connects outbound to GitHub over HTTPS port 443, picks up jobs, and executes them locally. Outbound connections traverse any NAT topology without router configuration.

"The best network architecture is the one that works within your actual constraints, not the one that works in the ideal case described in the documentation." — A hard-won lesson from two days of port forwarding debugging

Architecture Overview

The system has three distinct data flows: the CI/CD pipeline triggered by a git push, the GitOps loop driven by ArgoCD, and user traffic arriving via the Nginx ingress controller. Understanding how these three flows interact — and where they share infrastructure — is key to reasoning about the system's behaviour.

ArgoCD runs as a separate loop, independently of the CI pipeline. It polls the Gitea repository every three minutes and applies any changes to the charts/ directory. This means that chart configuration changes — replica counts, resource limits, ingress rules — are applied by ArgoCD, while application code changes are applied by the GitHub Actions runner. Both converge on the same cluster state.

The Three-Remote Git Configuration

One of the most useful patterns that emerged from this project is the three-remote git configuration. The developer laptop maintains three remotes simultaneously: origin points to GitHub over SSH, gitea points to the local Gitea instance over HTTP, and all is a special remote that pushes to both destinations with a single command.

bash 
# Set up the three-remote configuration
git remote add origin git@github.com:YOUR_USER/microk8s-devops-demo.git
git remote add gitea http://NODE1_IP:3000/YOUR_USER/microk8s-devops-demo.git

# The "all" remote fetches from GitHub but pushes to both
git remote add all git@github.com:YOUR_USER/microk8s-devops-demo.git
git remote set-url --add --push all git@github.com:YOUR_USER/microk8s-devops-demo.git
git remote set-url --add --push all http://NODE1_IP:3000/YOUR_USER/microk8s-devops-demo.git

# Daily workflow: one command, two destinations
git push all main

This configuration means that every push simultaneously updates GitHub (which triggers the CI pipeline) and Gitea (which ArgoCD polls for configuration changes). The authentication is handled transparently: the GitHub push uses the SSH key in ~/.ssh/id_ed25519 with no password prompt, and the Gitea push uses credentials stored in the macOS Keychain after the first successful authentication.

Never Embed Credentials in Remote URLs

A common mistake is allowing git to save credentials in the remote URL itself, producing entries like http://user:token@192.168.0.102:3000/... in .git/config. If that token is also stored in a global git credential helper shell function, it gets injected into every git operation regardless of remote, including pushes to completely unrelated hosts. Always use the OS credential manager (osxkeychain on macOS) and verify with git config --global --list | grep credential.

The Double NAT Problem

The original CI/CD design had GitHub's cloud-hosted runner SSH into NODE1 over the public internet. This requires the home router to forward an external port to NODE1's SSH daemon. In theory, straightforward. In practice, the network topology was more complex than expected.

Discovering the topology

The home network had three networking devices: an ISP-provided GPON ONT fiber modem, a TP-Link home router, and a mesh WiFi extender. Running ip route show default on NODE1 revealed the gateway was the TP-Link at 192.168.0.1. Checking the TP-Link's WAN IP in its admin interface showed 192.168.1.2 — a private address, not a public one. The ONT was at 192.168.1.1, performing NAT between the ISP and the TP-Link. Double NAT. 

Internet  (public IP: 45.186.209.180)
    │
    ▼
GPON ONT   192.168.1.1   ← NAT layer 1 (ISP-managed, menu locked)
    │
    ▼  gives TP-Link: 192.168.1.2
TP-Link    192.168.0.1   ← NAT layer 2 (we control this)
    │
    ▼  gives NODE1: 192.168.0.102
NODE1      192.168.0.102
NODE2      192.168.0.x
LAPTOP     192.168.0.x

Port forwarding in double NAT requires two rules: one on the ONT forwarding the external port to the TP-Link's WAN IP, and one on the TP-Link forwarding that port to NODE1. The TP-Link rule was straightforward. The ONT was the problem — its admin interface at 192.168.1.1 was not reachable from the LAPTOP (which sits on the 192.168.0.x network, on the other side of the TP-Link). A useful workaround: NODE1 can reach 192.168.1.1 because its packets traverse the TP-Link which knows both subnets. An SSH tunnel through NODE1 makes the ONT admin page accessible on the LAPTOP:

bash 
# On LAPTOP — forward local port 8181 to ONT admin via NODE1
ssh -L 8181:192.168.1.1:80 user@NODE1_IP -N &

# ONT admin page is now accessible at:
open http://localhost:8181

# Kill the tunnel when done
kill %1
How SSH Tunnelling Works

The -L 8181:192.168.1.1:80 flag tells SSH to listen on LAPTOP port 8181 and forward any traffic received there through the encrypted SSH connection to NODE1, which then forwards it to 192.168.1.1:80. From the ONT's perspective the request comes from NODE1. From the browser's perspective it is talking to localhost. The SSH connection is the pipe connecting the two.

The ONT's admin interface, when reached via the tunnel, lacked any DMZ or port forwarding options — the ISP had stripped those menus from the firmware. At this point the port-forwarding approach was abandoned in favour of the self-hosted runner, which requires no inbound connectivity at all.

The Self-Hosted Runner Solution

The GitHub Actions self-hosted runner is a lightweight agent that runs on NODE1 and polls GitHub's API for pending jobs. The connection is entirely outbound — NODE1 initiates HTTPS requests to api.github.com on port 443. This traverses any NAT configuration without modification, because NAT devices allow outbound connections by default and track the state to route response packets back correctly.

Installation

The runner is installed in a dedicated directory in the home folder of NODE1, separate from the project repository. After downloading and running the configuration script (with credentials provided by GitHub's setup wizard), the runner is registered as a systemd service:

bash 
# On NODE1 — install and start as a permanent system service
cd ~/actions-runner
sudo ./svc.sh install
sudo ./svc.sh start

# Verify
sudo ./svc.sh status
# Expected: active (running)

# Confirm the runner is connected to GitHub
sudo journalctl -u actions.runner.* -f
# Expected line: Listening for Jobs

The simplified workflow

Because the runner executes directly on NODE1 — where Docker, MicroK8s, and the local registry all live — the workflow file is dramatically simpler than the SSH-based alternative. No SSH setup, no rsync, no secrets for IPs or credentials. The NODE1 IP is resolved at runtime from hostname -I:

yaml 
jobs:
  deploy:
    name: Deploy on NODE1
    runs-on: self-hosted   # executes directly on NODE1

    steps:
      - uses: actions/checkout@v4

      - name: Build, push, upgrade
        run: |
          NODE1_IP=$(hostname -I | awk '{print $1}')
          REGISTRY="${NODE1_IP}:32000"

          docker build -t "${REGISTRY}/webapp:latest" app/
          docker push "${REGISTRY}/webapp:latest"

          microk8s helm3 upgrade webapp charts/webapp \
            --set "image.repository=${REGISTRY}/webapp" \
            --set "image.tag=latest" \
            --reuse-values --wait --timeout 5m
Add workflow_dispatch for Manual Triggers

The workflow's on.push.paths filter means pushes that only change documentation or the workflow file itself will not trigger a deploy. Add workflow_dispatch: to the on: block to enable a "Run workflow" button in the GitHub Actions UI — invaluable for testing the pipeline without making a dummy code change.

The Mission-Control Dashboard

The Flask application serves a single-page dashboard that demonstrates the key Kubernetes concepts at play: pod identity, node scheduling, database connectivity, and health probes. Refreshing the page causes the load balancer to rotate between replicas, changing the pod name displayed — a live demonstration of round-robin scheduling that is more viscerally convincing than any diagram.

The original template was a minimal dark card layout. The redesigned version adopts a mission-control aesthetic: a CRT scanline overlay in CSS, an animated grid background, a live UTC clock in the top bar, and a 12-column grid layout with panel hierarchy. The pod name is split into its stable prefix and randomised suffix, the database status renders with an animated pulse indicator, and the health probe panel shows all three probe states simultaneously. The entire UI is self-contained in a single Jinja2 template with no external CSS dependencies — critical for a LAN-only deployment with no guaranteed internet access.

Lessons Learned

Start with the constraint, not the ideal design

The SSH-from-internet pipeline was the obvious design. It was also the wrong one for this network. Spending time trying to make it work through a locked ISP modem was less productive than stepping back and asking: what does the self-hosted runner pattern cost, and does it eliminate the constraint? In this case it did — and simplified the pipeline as a side effect.

Double NAT is more common than the documentation implies

Most home networking guides assume a single NAT device between the internet and the LAN. GPON fiber deployments increasingly install a modem-router that performs its own NAT before traffic reaches the home router, creating a double NAT topology. The diagnostic is simple: check the home router's WAN IP address. If it is in a private range (192.168.x.x, 10.x.x.x), double NAT is present. The fix, if port forwarding is required, needs rules on both devices — or a call to the ISP to enable bridge mode on the ONT.

The git credential helper can be a hidden bomb

A credential helper shell function hardcoded in the global git config will inject its credentials into every git operation, regardless of the remote being accessed. This can result in a GitHub Personal Access Token appearing in the username field of an HTTP request to a completely unrelated Gitea instance on the LAN. The diagnostic is git config --global --list | grep credential. The fix is git config --global --unset-all credential.helper followed by re-adding only the OS keychain helper.

ImagePullBackOff on worker nodes almost always means hosts.toml

When worker nodes try to pull images from a local HTTP registry, containerd defaults to HTTPS and fails with a TLS error. The fix is a hosts.toml file that tells containerd to use plain HTTP for that specific registry address. This file must exist on every node that pulls images — not just the control plane where the registry runs.

Key Takeaways

What worked well

  • MicroK8s addon system reduced cluster setup from hours to minutes. The snap install, enable dns storage ingress registry helm3 sequence is genuinely fast on commodity hardware.
  • Self-hosted runner eliminated all network configuration complexity. The outbound-only model is more robust than inbound SSH for home lab use cases.
  • Three-remote git configuration kept the LAPTOP, GitHub, and Gitea perfectly synchronised with a single command, feeding both the CI pipeline and the GitOps loop simultaneously.
  • ArgoCD self-healing proved its value immediately — accidentally deleting a deployment in a kubectl experiment caused ArgoCD to restore it within three minutes without any manual intervention.
  • Gitea on the LAN made GitOps independent of internet connectivity. The cluster continued to self-heal correctly during an ISP outage because ArgoCD only needed to reach the local Gitea instance.

What would be done differently

  • Static IPs from the start. Using DHCP for NODE1 until late in the project meant the IP changed once during a router restart, breaking the Gitea remote URL, the ArgoCD app.yaml, and the port forwarding rule simultaneously. Reserve the IP via DHCP reservation on day one.
  • Separate SSH keys for every purpose. Using the same SSH key for personal git access and automated CI access means any compromise requires rotating credentials in two places. One key per use case is worth the small overhead.
  • Server-side apply for ArgoCD from the beginning. The standard kubectl apply fails for ArgoCD's CRDs because the annotations exceed the annotation size limit. The --server-side flag resolves this, but discovering the failure mode cost time.

Conclusion

A complete GitOps pipeline — from laptop keystroke to running pod — is achievable on hardware that costs less than a single month of equivalent cloud compute. The constraints of 4 GB RAM nodes and a locked ISP modem were not obstacles; they were the curriculum. Every workaround — the memory-tuned PostgreSQL manifest, the hosts.toml for HTTP image pulls, the self-hosted runner that eliminates inbound port requirements — produced a more resilient and better-understood system than the unconstrained version would have.

The full project, including all scripts, Helm charts, workflow files, and documentation, is available on GitHub. The README includes a quick-start that installs the complete stack in a single command, and a detailed manual that walks through every component and every failure mode encountered during construction. If you have two spare servers and a weekend, this is a worthwhile way to spend it.
